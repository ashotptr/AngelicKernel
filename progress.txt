25) 6.4.3.5.4.1 Type Specific Attributes
The meaning of the Type Specific Attributes field of the Extended Address Space Descriptor depends on the value of the
Resource Type field in the descriptor. When Resource Type = 0 (memory resource), the Type Specific Attributes field
values are defined per Memory Attribute Definitions in the UEFI Specification under section titled GetMemoryMap().
This is the only well-defined and OS-agnostic mechanism for describing specific resource descriptor mapping attributes.
For the architectural meaning behind the Memory Attribute Definitions, please see the ISA-specific binding in the
Calling Conventions section of the UEFI Specification at https://uefi.org/specifications.
Note: EFI_MEMORY_WC is treated as equivalent to MEM == 3 for the purpose of describing PCI(e) RC resources
matching prefetchable BAR requirements

74) XD, or 'Execute Disable'. 
If the NXE bit (bit 11) is set in the EFER register, 
then instructions are not allowed to be executed at addresses within the page whenever XD is set. 
If EFER.NXE bit is 0, then the XD bit is reserved and should be set to 0.

75) PK, or 'Protection Key'. 
The protection key is a 4-bit corresponding to each virtual address that is used to control user-mode and supervisor-mode memory accesses. 
If the PKE bit (bit 22) in CR4 is set, 
then the PKRU register is used for determining access rights for user-mode based on the protection key. 
If the PKS bit (bit 24) is set in CR4, 
then the PKRS register is used for determining access rights for supervisor-mode based on the protection key. 
A protection key allows the system to enable/disable access rights for multiple page entries across different address spaces at once.

79) You need to add a helper function to your vmm.c file and update your mapping function.
Step A: Add the Helper

C
// In vmm.c
void vmm_flush_tlb(uint64_t virtual_addr) {
    // "invlpg" tells the CPU: "Forget everything you know about this specific address."
    // The next time the CPU accesses it, it will be forced to look at the real Page Tables in RAM.
    asm volatile("invlpg (%0)" :: "r" (virtual_addr) : "memory");
}
Step B: Update vmm_map_page Your current code writes to the table but walks away without cleaning up. You should modify it like this:

C
void vmm_map_page(uint64_t virt, uint64_t phys, uint64_t flags) {
    // ... (Your existing code to find PML4, PDP, PD) ...

    // 3. Get PT
    uint64_t* pt = (uint64_t*)(pd[idx] & ~0xFFF);

    // 4. Set the Page Table Entry
    pt[PT_INDEX(virt)] = phys | flags;

    // 5. CRITICAL: Flush the TLB for this specific address!
    // If we don't do this, the CPU might keep using the OLD mapping it has cached.
    vmm_flush_tlb(virt); 
}
